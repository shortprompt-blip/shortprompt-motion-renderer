What if your smart home could understand natural language, answer questions about your sensors, and keep your data inside your own network? In this video, we’ll build the foundations of a local AI assistant using a Raspberry Pi, a small language model, and Home Assistant.

First, understand the architecture. Home Assistant is the automation platform. The Raspberry Pi runs the language model and exposes a local API. Home Assistant sends a request to that model, receives its interpretation, and then performs only the actions you have allowed it to access. The model is not replacing your automation system. It is adding a language interface to it.

For this tutorial, assume Home Assistant is already running on a separate machine, such as a Home Assistant Green, a mini PC, or another Raspberry Pi. We’ll use a second Raspberry Pi 5 as the AI host. Keeping them separate makes the roles clear, and lets you restart or experiment with the model without taking your home automations offline.

For a practical starting point, choose a Raspberry Pi 5 with eight gigabytes of RAM, a reliable power supply, active cooling, and a fast SSD or quality storage. A four-gigabyte board can work with smaller models, but memory is shared with the operating system and other services. An eight-gigabyte model gives you more room to experiment.

Now, a realistic expectation. A Raspberry Pi 5 running a language model on its CPU is not a desktop GPU. Small quantized models, around one to three billion parameters, are the sensible starting range for simple commands, classification, and short answers. Responses may take several seconds. Long prompts and large models can become very slow. This project is about a private, low-power assistant for focused tasks, not a replacement for a high-end cloud model.

There is also an accelerator option. Raspberry Pi AI HAT Plus 2 uses a Hailo-10H processor, has eight gigabytes of dedicated memory, and is rated at forty TOPS. Raspberry Pi documents local LLM and vision-language model support for this board, with models up to roughly six billion parameters. It is not the same as the original AI HAT Plus: the original HAT Plus is designed for vision workloads and does not support LLMs. We’ll keep the main integration path straightforward, and show the HAT Plus 2 as a separate hardware upgrade because it uses Hailo’s own software stack and supported model list.

Let’s install the model server on the AI host. Update Raspberry Pi OS first, then install the ARM64 build of Ollama using the official installation instructions. After installation, start the service and check that it responds locally. The exact installer and model tags can change, so use the official Ollama instructions rather than copying an old script from an unverified tutorial.

Next, choose a model that matches the job. A one-billion-parameter model is useful for a basic installation test, but do not assume it will reliably call Home Assistant tools. For device control, use a tool-capable model. Home Assistant currently lists Qwen three four-billion instruct as its default Ollama model. It is a roughly four-billion-parameter model with a download around two-and-a-half gigabytes, and it may respond slowly on a Raspberry Pi five CPU. Start with a modest context window, such as two thousand forty-eight or four thousand tokens, and monitor memory. Use the model’s current tag from the Ollama library. Once downloaded, run a simple prompt from the terminal. If it answers while the internet connection is disabled, you have verified that inference is happening locally, with the model already stored on your device.

Now connect Home Assistant. Open Settings, Devices and services, choose Add integration, and search for Ollama. Enter the local network address of the Raspberry Pi that runs the model server, using its IP address and Ollama’s configured port. Do not use localhost here: from Home Assistant, localhost means the Home Assistant machine itself, not the other Raspberry Pi. If you use a firewall, allow access only from your trusted home network.

After the integration connects, add a conversation agent and select the model you downloaded. Start with a modest context window. A larger context can include more conversation and more exposed entities, but it also uses more memory. If the model supports tool calling, enable Home Assistant’s device-control tools for this assistant.

Here is the first practical example. In Home Assistant, expose only the light you want the assistant to control. Open Assist and type: turn off the desk light, then turn on the hallway light. The model interprets the sentence, Home Assistant receives the tool call, and the two exposed light entities change state. This is not a fake automation: the important step is that the assistant can only access the entities you explicitly exposed.

Example two: ask, is the bedroom temperature above twenty-four degrees? Expose the relevant temperature sensor. The assistant can read its current state and answer using the value Home Assistant provides. Keep the question simple and check the response against the sensor card. A small local model can misunderstand a question, so the dashboard remains your source of truth.

For the third example, expose a script that you have already created and tested. The script might set a night scene: turn off selected lights, leave a hallway light at a low brightness, and set the thermostat to a preset. Ask the assistant to activate the night scene. Home Assistant runs the predefined script, rather than allowing the model to invent a chain of sensitive actions. This is a safer pattern: let the AI choose among a small set of approved tools, and let deterministic Home Assistant scripts handle the actual sequence.

You can also build ordinary automations around sensor thresholds, schedules, presence, and device states. Those rules should remain native Home Assistant automations. You do not need an LLM to decide whether a temperature is above a fixed number. Use the language model when language understanding adds value, and use normal automation logic for precise, repeatable conditions.

Before relying on the assistant, test failure cases. Ask it to control an entity that is not exposed. It should not have access. Disconnect the AI host and confirm that your existing Home Assistant automations still work. Restart the model server and test again. Check logs, memory usage, and temperatures while the model is answering. Active cooling matters for sustained workloads.

Finally, consider privacy and security. Local inference means prompts can stay on your own hardware, but it does not automatically make every part of the system private. Keep the model server off the public internet, use a reserved IP address, update your software, and expose the minimum entities. Never give a small model unrestricted control over locks, alarms, garage doors, or other safety-critical devices. Require confirmation or keep those actions outside the assistant.

The result is a useful local AI layer: a Raspberry Pi running a small language model, Home Assistant providing the device state and permissions, and scripts and automations performing the actual work. Start small, measure response time, and add one capability at a time. If you want more speed or larger models, investigate the Raspberry Pi AI HAT Plus 2 and verify the supported Hailo models and API compatibility before planning your integration.
