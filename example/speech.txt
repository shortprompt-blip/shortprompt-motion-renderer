What if you could build a character animation by giving an AI model a few poses, instead of authoring every transition by hand? That is the idea behind NVIDIA MotionBricks. It is not a text-to-video generator, and it is not a one-click animation app. It is a real-time motion generation system for developers working with 3D characters and humanoid robots. In this tutorial, we will install the official project, generate a first transition with the Inbetweener, and then look at how reusable interactions work.

Before installing anything, understand what MotionBricks actually does. The model receives four recent poses from a character, plus between one and four target poses that describe where the character should go. It predicts the movement connecting the current motion to those targets. One target can define a final posture and stopping point. Additional targets can describe velocity, acceleration, and momentum at the destination. The application still decides the goal. MotionBricks generates the movement needed to reach it.

The same generation approach supports two character layouts in the official release: the SOMA human body model and the Unitree G1 humanoid robot. The repository includes pretrained ONNX models, a Python runtime, interactive demos, and editors for building reusable interactions. The examples are reference applications for developers. They are not a finished animation package or a turnkey Unreal Engine integration. The Unreal Engine showcase shown in the research material is not included in this release.

Now check the requirements. The official project targets Windows and Linux on x86-64. Its Python package requires Python 3.12 or newer. The runtime depends on an NVIDIA GPU because it uses TensorRT, together with Warp and Newton. NVIDIA says the demos were tested on an RTX 4090. That is the documented test configuration, not a universal minimum requirement or a guarantee that every other GPU will work. TensorRT compatibility, driver versions, CUDA runtime packages, and available GPU memory all matter. If you are using a laptop GPU, do not assume it behaves like the desktop version with the same product name.

For the setup, install Git, Git LFS, and uv first. Git LFS is important because the repository contains large assets. Open a terminal in the folder where you keep development projects. Clone the official NVIDIA repository, enter the new folder, pull the large files, and synchronize the environment. The commands are shown on screen. The first launch of each model and precision builds a TensorRT plan. That can take a few minutes. Later launches reuse the cached plan, so they should start more quickly. Do not interrupt the first build just because it appears slower than a normal application launch.

Once the environment is ready, start with the Inbetweener. This is the simplest way to understand the model because it exposes the target poses directly. Launch the demo with the command shown here and confirm that the character selector is set to SOMA. The viewer has a 3D scene and a control panel. You can orbit, pan, and move the camera with the documented mouse and keyboard controls. The important part is the Target Poses list. Each target is a point the generated motion must reach.

For a first test, select the End target and move it forward along the character's travel direction. Then press Generate. MotionBricks creates a transition from the character's recent motion to that target. This first result is intentionally simple: it proves the generation loop is working. Next, enable the skeleton and velocity visualizations. The four context poses show the recent motion history. They matter because the model needs more than a static starting pose; they also describe how the character is already moving as it enters the transition.

Now add intermediate targets. The official guided tutorial builds a duck-under interaction. It samples poses from a motion clip, places an Entry target and a Duck-under target between Start and End, and adjusts the target settings. In the documented example, the Entry pose uses frame 199 and the Duck-under pose uses frame 328 from the supplied BVH clip. These are tutorial-specific sample values, not universal settings. The number of poses used and the transition-early setting influence how closely the character approaches the target and how much existing momentum carries through the transition.

There is another important control: Tokens to Generate. MotionBricks chooses a short transition length. Each motion token yields four raw frames. The tutorial uses a range of eight to fourteen tokens for its Inbetweener targets, which corresponds to thirty-two to fifty-six raw frames. A longer distance between targets may need more tokens. A short distance may need fewer, otherwise the character can generate unnecessary movement. Generate again and inspect the full sequence. You are authoring the goals; the model is filling in the motion between them.

The next level is a Smart Primitive. Think of it as a reusable, pose-based interaction around an area in the scene. The editor lets you define an Interaction Box, a Pivot, and target poses. The interaction box identifies where the behavior can begin. The pivot rotates and translates the authored sequence so that a character can approach from a different direction without first walking to the original authoring path. In the guided example, the pivot rotates to face the approach direction and can slide the sequence sideways by up to half a metre. The target poses define the action inside the interaction area.

After saving the Smart Primitive, open the Scene Editor and place it in a scene. Then run Scene Preview. This reference application combines locomotion, interaction detection, behavior logic, and generated motion. You can walk the character toward the interaction area and trigger the behavior. The preview also exposes useful diagnostics, including target poses, context poses, blend-space poses, velocity, foot contacts, and model timing. This is where you can see the difference between a model demo and a complete application: the host application manages input, state, and target selection, while MotionBricks generates the transitions.

A key idea is chaining. One generation is deliberately short. The runtime plays the generated motion, records the poses that were actually played, and feeds the last four poses into the next generation. That rolling context lets the application build continuous movement from many short predictions. It is also why the application must manage timing and state carefully. If your integration chooses poor targets, the model cannot infer the interaction you intended. MotionBricks is a motion generator, not a substitute for the logic of your animation system.

What should you take away? MotionBricks is interesting when you need controllable, pose-conditioned movement for characters, humanoid simulation, or interactive scenes. It gives developers a different way to author transitions and interactions, using target poses and reusable primitives rather than relying only on hand-authored clips. But it requires an NVIDIA-oriented development environment, and the example apps are there to teach the integration pattern. Start with the Inbetweener, understand context and target poses, then move on to Smart Primitives and Scene Preview.
