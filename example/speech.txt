What happens when GPT-6 Astra is not just asked to write code, but is given control of an entire computer?

For this case study, the instruction is deliberately simple: open the project, find why the 3D application is failing, fix the issue, run the project, test the main interaction, and verify the final build.

The important part is that the agent has to work through the graphical environment.

Astra starts on the desktop.

It opens the project from File Explorer instead of receiving a preselected file.

It launches the local development environment and opens the application in Microsoft Edge.

The first browser run exposes a failure: the block-placement interaction crashes.

Now the task changes from generation to diagnosis.

Astra reads the terminal output and follows the stack trace back into the project.

The failure points to the placement module.

The active block is being passed into the placement routine before its world transform has been initialized.

The renderer expects a valid position object, but the factory is returning the object before that state exists.

Astra does not work around the error in the browser. It changes the implementation.

The block factory is updated so every new block receives its transform state when it is created.

The placement function can then operate on a valid world position instead of checking for an object that may not exist.

Now Astra goes back to the terminal.

First it runs the targeted placement test.

Eight tests pass.

Then it runs the full regression suite.

Twenty-one tests pass with zero failures.

But unit tests are not enough for a computer-use task.

The agent rebuilds the application and returns to the browser.

This time it performs the interaction itself through the desktop interface.

The block can be placed, the tower state updates, and the browser continues running the game loop without the original exception.

Finally, Astra verifies the production build.

The application is rebuilt, the preview is launched, and the browser is checked again against the same interaction that originally failed.

This is the part of computer use that matters.

The model is not simply producing text or returning a code patch.

It is coordinating multiple interfaces: File Explorer to locate the project, the terminal to execute commands, the browser to reproduce the failure, the source files to understand the implementation, and the browser again to verify the result.

The computer becomes part of the reasoning loop.

Observe the screen.

Choose an action.

Inspect the result.

Update the hypothesis.

Change the implementation.

Run the software again.

And verify whether the original failure is actually gone.

That is very different from asking an AI to generate a code snippet.

It is an end-to-end software workflow carried out through the same interfaces a developer would normally use.

And in this case study, the success condition is simple: the bug is reproduced, the root cause is isolated, the implementation is fixed, the regression suite is green, and the final application works in the browser.

That is the capability we wanted to test: not whether an AI can write code, but whether it can use a computer to complete the engineering task.
